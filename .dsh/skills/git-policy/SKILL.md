# Git 提交规则

## 核心流程（最重要）

**所有提交（不只推送）前必须经用户确认。** 流程：

1. 改动在工作区**攒够一个可描述的逻辑单元**（功能完整实现 + 测试通过 + 文档同步，或一个完整修复）；
2. 提交前向用户**展示**：改了哪些文件（`git diff --stat`）+ 拟用的提交信息；
3. **用户明确同意后**才 `git commit`；
4. 推送 GitHub 前同样须用户确认。

> 为什么：AI 无法保证一次改动就正确，功能要迭代、bug 要复现验证、文档要和用户对齐。
> 未经确认直接提交 = 把 git 当保存按钮，会产生多次返工提交。攒够 + 确认 = 干净历史 + 用户把关。

## 提交粒度

**一个提交 = 一个可独立描述的逻辑单元（功能 / 修复 / 文档任务），不是一次文件修改。**

- 开发一个功能：**整个功能做完**（实现 + 测试 + 文档）再提交一次；
- 小修复：攒够相关改动合并提交，或并入所属功能；
- 文档更新：随功能一起提交（如 `feat: xxx（含文档）`），或同类文档合并为一次 `docs:`；
- 探索性工作：不产生价值的直接删除不提交；有价值的结论压缩成一份备忘合并提交。

## 提交时机

- ✅ 完成一个可描述的逻辑单元 + 用户确认时；
- ✅ 需要切换任务前（checkpoint，先向用户确认再提交）；
- ❌ 每次文件保存 / 每次命令执行后 / 未经用户确认。

进行中的工作可留在工作区不提交；跨天或切换任务前，先向用户确认是否提交当前进度。

## 提交信息格式

```
<type>(<scope>): <一句话描述>

type: feat / fix / docs / refactor / chore / test
scope: web / backend / script / docs（可选）
```

- 描述用中文，简洁说明"做了什么"；
- 同一主题的多条改动（实现 + 文档）合并在一个提交里，不要拆散；
- 提交信息里避免特殊字符导致 shell 解析问题（用引号包裹整条 message）。

## 安全与卫生

- 提交前检查 diff（`git diff --stat`、敏感字段扫描）。
- 不提交敏感信息（密码/私钥/密钥文件）、生成物（.venv / node_modules / dist / data / 缓存）。
- 推送前确认 `.gitignore` 覆盖所有生成物。
